# Portable Railway + Xray XHTTP/REALITY

A portable Railway deployment variant derived from the verified production baseline.

## 🚀 Deploy on Railway

**The portable branch is Template-first.** The intended user flow is:

```text
README
  ↓
🚀 Deploy on Railway
  ↓
Railway Template
  ↓
Login / Sign up if needed
  ↓
Review the Template deployment configuration
  ↓
Confirm
  ↓
Deploy
  ↓
Automatically create a new Railway Project / Service
  ↓
Build
  ↓
Start
```

Railway's official Template deployment flow is designed for a pre-configured project: after a user selects a template, they configure any required variables and click `Deploy`; Railway then creates the new project and deploys the services defined by the template. citehttps://docs.railway.com/templates/deploy

### Official Deploy on Railway button

The final README button must use the **real Template URL generated by Railway**:

```markdown
[![Deploy on Railway](https://railway.com/button.svg)](REAL_RAILWAY_TEMPLATE_URL)
```

Do **not** use `https://railway.com/new/github` as the primary button. That URL opens Railway's generic GitHub repository picker and requires manual repository selection before deployment.

The repository intentionally does not invent a Template URL. Railway creates the Template URL after the Template is created in the Railway workspace. Once that real URL exists, it should replace the placeholder above.

### What the Template must contain

The Template should be created from this portable branch and pre-configured with:

```text
Source:
  GitHub repository → this portable branch

Build:
  Dockerfile

Application / Gateway target:
  8080

Public Networking:
  Railway-provided domain enabled

TCP Proxy:
  enabled
  target/application port = 8080

Healthcheck:
  /health

Persistent Volume:
  /data
```

Railway's Template editor supports configuring the GitHub source/branch, variables, public networking with TCP Proxy or HTTP, healthcheck, and volumes. citehttps://docs.railway.com/templates/create

### One-time Template creation

The repository contains the exact setup checklist in:

```text
deploy/RAILWAY_TEMPLATE_SETUP.md
```

The Template itself is created once in the Railway workspace. After creation, Railway provides the shareable Template URL and the official `Deploy on Railway` button markup. citehttps://docs.railway.com/templates/publish-and-share

After the real Template URL is inserted, the generic GitHub picker is no longer part of the normal deployment path.

### GitHub fallback only

If the Template has not yet been created, the generic GitHub flow remains available as a fallback:

```text
README
  ↓
Railway GitHub entry
  ↓
Login / GitHub authorization
  ↓
Select repository
  ↓
Verify Repository / Source
  ↓
Deploy Repo
```

This is intentionally **not** described as one-click deployment because Railway's GitHub flow requires repository selection. Railway's current quick-start documents this repository-selection flow explicitly. citehttps://docs.railway.com/quick-start

## Portable deployment architecture

```text
                    Railway Public Networking
                              │
                     HTTPS / current domain
                              │
                              ▼
                        Gateway :$PORT
                     (default target :8080)
                              │
             ┌────────────────┼─────────────────┐
             │                │                 │
           /sub/*           /health           /ready
             │
             └────────────── site/ + subscription

HTTP/XHTTP path /xhttp ───────────────► 127.0.0.1:10086

Railway TCP Proxy ────────────────────► 127.0.0.1:10087
                                          │
                                      REALITY+XHTTP
                                          │
                                  7 verified SNI nodes
```

The subscription contains **8 nodes**:

1. One HTTPS + TLS + XHTTP node using the current Railway public domain.
2. Seven XHTTP + REALITY nodes using the current Railway TCP Proxy endpoint and the verified SNI pool.

## Portable deployment checklist

### 1. Deploy from the Railway Template

Preferred production flow:

```text
Deploy on Railway
  ↓
Login / Sign up
  ↓
Review Template configuration
  ↓
Confirm
  ↓
Deploy
```

Railway then creates the new project/service and deploys the services defined by the Template. citehttps://docs.railway.com/templates/deploy

### 2. Public Networking

The Template should enable Railway Public Networking. The runtime uses the current `RAILWAY_PUBLIC_DOMAIN` value.

The application listens on Railway's injected `PORT`; the intended Gateway target is `8080`.

### 3. TCP Proxy

The Template should provision the Railway TCP Proxy with **application/target port `8080`**.

Railway generates the TCP Proxy domain and external proxy port. The external port is **not fixed** and must never be copied from an older deployment. citehttps://docs.railway.com/networking/tcp-proxy

The runtime reads:

```text
RAILWAY_TCP_PROXY_DOMAIN
RAILWAY_TCP_PROXY_PORT
RAILWAY_TCP_APPLICATION_PORT
```

The resulting path is:

```text
<current TCP proxy domain>:<current random external port>
                         ↓
                    application :8080
```

### 4. Persistent Volume

Attach a Railway Volume at:

```text
/data
```

The runtime persists generated identity, key, encryption and subscription material under `/data`.

### 5. Healthcheck

Configure `/health` as the Railway healthcheck. The gateway also exposes `/ready` for diagnostics.

## Runtime discovery

No deployment-specific Railway hostname or TCP external port is hard-coded in this portable variant.

Runtime values are authoritative:

```text
RAILWAY_PUBLIC_DOMAIN
RAILWAY_TCP_PROXY_DOMAIN
RAILWAY_TCP_PROXY_PORT
RAILWAY_TCP_APPLICATION_PORT
PORT
RAILWAY_VOLUME_MOUNT_PATH
```

The TCP Proxy target/application port must resolve to the project's fixed Gateway target of `8080`; the public hostname and TCP Proxy external port are generated per Railway deployment.

At startup the log prints only non-secret routing information:

```text
[startup] Railway public domain: ...
[startup] TCP proxy: ...
[startup] Gateway: 0.0.0.0:...
[startup] Xray REALITY: 127.0.0.1:10087
[startup] Xray HTTPS/XHTTP: 127.0.0.1:10086
```

Private keys, UUIDs and subscription tokens are never printed.

## Subscription endpoints

After startup, the current subscription endpoints are written under `/data`:

```text
subscription_primary_url.txt
subscription_fallback_url.txt
subscription_endpoints.txt
```

They are generated from the current instance values:

```text
PRIMARY=https://<CURRENT-RAILWAY-PUBLIC-DOMAIN>/sub/<CURRENT-TOKEN>
FALLBACK=http://<CURRENT-RAILWAY-TCP-PROXY-DOMAIN>:<CURRENT-RAILWAY-TCP-PROXY-PORT>/sub/<CURRENT-TOKEN>
```

The seven REALITY/XHTTP nodes also use the current Railway TCP Proxy domain and current Railway-assigned external port.

## First deployment validation

After a Template deployment, verify in this order:

```text
1. Template confirmation page shows the intended service/source
2. Deploy is confirmed
3. New Railway Project is created
4. Build succeeds
5. Container starts
6. /health returns 200
7. /ready returns 200
8. startup log shows the NEW public domain
9. startup log shows the NEW TCP Proxy host:port
10. /data/subscription_primary_url.txt contains the NEW public domain
11. /data/subscription_fallback_url.txt contains the NEW TCP Proxy domain + RANDOM external port
12. HTTPS subscription returns 8 nodes
13. Client tests the HTTPS/XHTTP node
14. Client tests the REALITY/XHTTP nodes
```

Do not treat a successful Docker build as proof of a successful runtime. The build and deploy stages are separate.

## Security / repository hygiene

Never commit:

- UUIDs
- REALITY private keys
- REALITY public keys generated for a deployment
- VLESS encryption/decryption material
- subscription tokens
- `/data` runtime artifacts
- Railway API/project tokens

The repository contains only generation logic and the verified SNI pool.

## Stability rule

This branch is a **portable deployment variant**, not a replacement for the current production baseline.

Keep changes isolated here until a fresh Railway deployment has passed:

- website test
- `/health`
- `/ready`
- HTTPS/XHTTP client test
- TCP Proxy/REALITY client test
- subscription node-count and hostname validation

Only after those tests pass should the changes be considered for promotion to the production baseline.
